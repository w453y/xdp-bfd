Scale validation at 64 concurrent sessions (32 per peer VM). Engine at
full slot capacity. pcap (4.3M pkts, too large for the repo) retained
offline; derived numbers below.

Bugs found and fixed by this test, in order of discovery:
1. Slot port range collided with bfdd. Stock bfdd binds per-session
   sockets bottom-up from 49152 even in distributed-dataplane mode.
   Our slots moved to 65472-65535 (top of the RFC 5881 range); bind
   failure now cached per slot and logged once.
2. Upstream FRR: bfdd's dplane client truncates the initial session
   burst at 8KB. 64 sessions x 406B (ADD+UPDATE) = 26KB into an 8KB
   buffer; exactly 20 delivered (8120B on the socket, zero TCP
   backpressure), dropped sessions marked delivered and never resent.
   Workaround: empty bfd block in frr.conf, add peers via vtysh after
   the dplane connects. Issue report pending.
3. Engine: AdminDown had no exit. dp_handle_add cleared the flag but
   nothing restarted the FSM; fixed with an explicit transition.
4. Engine: per-slot TX sockets bound INADDR_ANY, so routing sourced
   every session from the primary address. Combined with our
   spec-mandated your_disc drop and a peer holding a stale remote
   disc, this deadlocked one session permanently. Sockets now bind
   the session's local address (rebind on slot reuse).
5. Engine: graceful-restart reconcile only unmarked orphans on the
   adopt-by-address path (bfdd restart, new lids). A dplane
   reconnect with stable lids left all sessions marked orphaned and
   the sweep tore down 64 live sessions. Any message naming a lid
   now unmarks it.

Results at 64:
- Bring-up: 64/64 via incremental adds, 64 slot sockets bound
  65472-65535, sessions establishing while later adds still arrive.
- Mass kill (pkill -9 bfdd, 32 sessions): all 32 detected in
  30.1-32.9ms across three 3ms sweep buckets; no drift vs N=1.
  Surviving 32 untouched. Peer's watchfrr respawned bfdd; all 32
  re-established unattended in ~6s.
- L3 stress 120s: one correlated flap event. 19 of 64 sessions
  declared detect timeout in the same sweep pass (~32.5ms silent),
  recovered in ~50ms. Wire truth: those slots' TX gaps were 23-46ms
  while all others stayed <=16ms and the peers kept pacing - a
  single DUT-side RX-softirq stall (hrtimer stressors) while the
  sweep timer kept running. This is the design's false-flap
  boundary: RX-clocked TX is scheduler-immune but not
  softirq-starvation-immune, and one starved context flaps every
  session hashed onto it at once. Zero such events at N<=16 under
  identical stress; one event/120s at N=64.

Committed evidence: bfd-m6-64sess-flapwindow.pcap.gz (the 19-session
correlated flap, 20s) and bfd-m6-64sess-killwindow.pcap.gz (the
32-session mass kill, 20s). Full 339MB capture retained offline.
