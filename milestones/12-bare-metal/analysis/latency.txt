irq/s: all enp1s0 vectors. Already about one interrupt per packet at this
rate, which is why rx-usecs alone changes nothing.

With ASPM off, authenticated classes sit about 7 us above the rest at p50
(L5r: auth-keyed 39.1, auth-meticulous 39.3, base 33.1): the digest,
computed in XDP. With ASPM on it was lost in the wake-up.

A first run of L5-L8 with gi1 mirrored both ways is not used: the peer's
packets then appear twice, the analyser pairs replies with the second
copy, and 7-12% fewer pairs matched (539k-507k), the slow ones. p50 read
17 us there. L5r-L8r repeat them with the mirror as for L0-L4.

Why the kernel cannot do it here:
  ACPI FADT declares the system doesn't support PCIe ASPM, so disable it
  acpi PNP0A08:00: FADT indicates ASPM is unsupported, using BIOS configuration
The firmware enables L1 itself and keeps ASPM; pcie_aspm.policy is refused
and pcie_aspm=off leaves the firmware's L1 in place. The link advertises
an L1 exit under 16 us.

Floods with ASPM off (flood_hw.py, 10 s, about 1.2M frames/s):
  rx-usecs 3  C  xdp 175 ns/frame engine 6.2% softirq 2.8%  0 flaps
  rx-usecs 3  I  xdp 312 ns/frame engine 4.9% softirq 3.8%  0 flaps (3 runs)
  rx-usecs 0  C  xdp  90 ns/frame engine 1.5% softirq 2.0%  0 flaps
  rx-usecs 0  I  xdp 170 ns/frame engine 3.8% softirq 1.1%  the target, on the peer (5 runs)
Under a flood NAPI stays in polling, so rx-usecs 0 adds no interrupts.
Arm I forges the real session 10.66.0.12/.112 with its discriminators;
that session went down on the peer in all five runs at rx-usecs 0, in
none of three at 3, and in the first flood run of 2026-09-30 (rx-usecs 3,
ASPM L1). No other session went down in any of them, and the engine
recorded no flap.

m1 left as installed: ASPM L1, EEE on, rx-usecs 3, all C-states.
